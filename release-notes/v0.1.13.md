# Spidey v0.1.13

## What changed

**Cost, cut by roughly 5x — this is the release for anyone paying per token.** A real Sarvam
bill showed **1.4M input tokens (₹39.78) against 12.9K output (₹0.95)**: 97% of the spend was
input the app had already sent. The cause was in how the conversation was built.

Every step sent the whole conversation, and most of it was old screen listings. One listing is
about **2,500 tokens**, and up to 22 messages were carried into each request — tens of
thousands of tokens per step, resent every step, for screens the agent had already finished
with. Fixed:

- **Only the two most recent screen listings are kept in full.** Older ones collapse to a
  short marker. The turn itself stays, so tool calls and their results remain paired.
- **The opening screen is dropped** as soon as anything newer exists.
- **An unchanged screen is no longer re-sent.** If an action leaves the screen exactly as it
  was, the model gets one line saying so instead of the same 2,500 tokens again — which
  matters most on repetitive runs, where the spend was worst.
- **Shorter element lines** — labels capped at 60 characters, and the resource id is only
  shown when there is no text to target by.

A typical request drops from about **32,000 tokens to under 7,000**.

What is left is fixed overhead: the system prompt (~950 tokens) and the tool definitions
(~970 tokens) are sent on every request and cannot be dropped. If your provider offers
**prompt caching**, turning it on makes both close to free after the first call.

**The usage guide** ([docs/USAGE.md](docs/USAGE.md)) now has a cost section explaining all of
this, plus practical ways to spend less.

**New tests:** `ContextCompactorTest` pins the compaction rules, including that tool calls and
results stay paired.
