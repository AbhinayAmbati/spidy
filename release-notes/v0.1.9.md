# Spidey v0.1.9

A native Android AI agent. You type a task in plain language — *"Open Chrome and search
for Kubernetes"* — and it plans the steps, drives your phone through Android's official
APIs, watches what happens on screen, and keeps going until the task is done or it needs
your approval.

This release is a full audit of the tool layer **and** of the conversation the model is
actually given. Several defects, all fixed.

---

## What changed

### 1. The agent now *must* call a tool — it can no longer drift into chat

This is the fix for *"The model kept replying with text instead of acting."* The loop was
sending `tool_choice: "auto"`, and the Anthropic and Gemini providers were sending **no
tool choice at all**. Under `auto`, a model is free to answer with prose — and that is
exactly what it did mid-task, stalling the run.

An agent turn is never a chat turn: it must act. So every provider now **forces a tool
call** — `required` for OpenAI-compatible endpoints, `{"type":"any"}` for Anthropic,
`functionCallingConfig: ANY` for Gemini. A model can no longer stop the task by talking.

### 2. The conversation now reads as real tool use

Each provider expects a tool call and its result to be **paired**. The loop was instead
sending the model a plain-text line — `"action: click"` — followed by a user message. None
of the three APIs recognise that as tool use, so the model could not reliably tell what it
had already done.

It now sends a proper tool-call turn and a proper tool-result turn for every action:

| Provider | Assistant call | Result |
| --- | --- | --- |
| OpenAI | `tool_calls[]` with `id` + `function` | `role: "tool"` with `tool_call_id` |
| Anthropic | `tool_use` block | `tool_result` block in a user turn |
| Gemini | `functionCall` part | `functionResponse` part |

### 3. A failed action no longer blinds the model

When a tool failed, the model was told only *that* it failed — with no screen attached. It
had nothing left to reason about, which is a large part of why it gave up and answered with
prose. A failure now carries the fresh screen as well, so the model can see what actually
happened and try something else.

### 4. Resource-id matching accepts what the model was shown

The observation displays the short id (`id=url_bar`) while the platform needs the
fully-qualified one (`com.android.chrome:id/url_bar`). The model echoes back what it was
shown, and the lookup silently failed. Both forms now work, and the schema description
matches what the model actually sees.

### 5. Touching a stale element can no longer kill the task

An element captured by an earlier screen can go stale, and reading or clicking one throws.
Clicks and long-presses are now guarded, so a stale reference becomes a clean "could not
find it" the model can react to, instead of an exception that ends the run.

### 6. The screen listing tells the model what each element *is*

Widget type is now included (`<EditText>`, `<Button>`), because an `EditText` is typeable
and a `TextView` is not. Previously the model had to guess.

### 7. Failures are visible to you

A failed step was a bare red cross. Steps now name their target — *Tapping "Search"* rather
than *Tapping an element* — and a failed step shows **why** underneath it, in the app and in
history.

## The audit

Every one of the **16 tools** was checked against the schema the model is given, the
validation it runs, and the code that executes it. Findings:

- Schemas, required fields and executed fields all agree — no mismatches. Good.
- **No schema asks the model for `action`.** This is the property that matters: the tool's
  *name* is the action and arrives separately from the arguments. A schema that also
  declared `action` would make the model repeat it, and it could then contradict the
  function it actually called. There is now a test asserting no schema does this.
- Every schema property is a field `AgentAction` can actually read, every `required` entry
  is a declared property, and the `target` object offers exactly the fields the matcher
  understands — all pinned by tests.

New tests: `ToolSchemaContractTest` (the schema/action contract above) and
`ProviderToolTurnTest` (the tool-call and tool-result shapes each provider must emit).

## Install

1. Download **`spidy.apk`** below.
2. Allow installing from the app you're installing from:
   **Settings → Apps → Special app access → Install unknown apps** → pick Chrome / Files / Drive → **Allow**.
3. Play Protect will warn — *"Unsafe app blocked"* or *"doesn't recognise this app's
   developer"*. Expected: the signing key is new and has no install history. Tap
   **More details → Install anyway**.
4. Upgrades cleanly over earlier Spidey builds. If it refuses, uninstall the old one first.

**After updating, turn accessibility off and back on once.** The system caches the previous
declaration, so it will not re-bind on its own.

**Requires Android 8.0 (API 26) or newer.**

### Try this first

> Open Chrome and search for Kubernetes.

Expect: opening Chrome → tapping the address bar → typing → pressing search → done. If a
step fails now, the reason is shown under it — tell me that line and I can act on it.

## Features

- **Home** — one spacious field asking *"What should I do?"*, with voice input and recent tasks.
- **Live task view** — step-by-step status with failure reasons, pause/resume, and Stop.
- **Confirmation gate** — anything sensitive (send, pay, delete, call, install, confirm)
  pauses and waits for an explicit **Allow**.
- **History** — every task grouped by day, openable to see the actions performed, apps used,
  duration and result.
- **Bring your own key** — OpenAI, Anthropic, Google Gemini, Sarvam AI, OpenRouter, or any
  OpenAI-compatible endpoint. Your key is encrypted on-device and sent only to the provider
  you choose.
- **Model picker** — suggested model ids per provider, with a "Custom model…" escape hatch.
- **Memory** — learns app shortcuts from tasks you actually run, viewable and deletable.
- **Terms of Service** — in-app, under Settings → Legal.

## Permissions

| Permission | Why |
| --- | --- |
| **Accessibility** | Required. Lets the agent see and control supported interfaces. You can stop it any time. |
| **Notifications** | Shows progress while a task runs. Optional notification access enables reading notifications. |
| **Internet** | To reach the AI provider you configured. |

Spidy does **not** request `QUERY_ALL_PACKAGES`; it resolves launchable apps through a
declared intent query.

## Privacy and security

- Your API key is encrypted on-device and sent only to the provider you chose.
- Screens are summarised into a short list of labelled, interactive elements before anything
  is shared with a model — raw accessibility trees are never dumped.
- Task history, memory and preferences are local-only, and excluded from device backups.
- The model is treated as **untrusted input**. It can only act through the fixed tool
  surface, and every action passes a validator first.
- Android restrictions are explained rather than bypassed.

---

## Known limitations

- **Real-device coverage is still thin.** The tool layer is now consistent and tested, but
  selector heuristics have not been exercised across Chrome, Settings, YouTube, Gmail and a
  messaging app. A step may still fail to find the element it wants — you will now see why.
- **Forcing a tool call requires provider support.** All three first-party APIs support it.
  An unusual custom gateway may reject `tool_choice: "required"`; the error is surfaced
  rather than swallowed.
- **No screenshots.** Apps that expose nothing useful to accessibility are out of reach.
- **Terms of Service are a template.** Placeholders for the legal entity, jurisdiction and
  contact address are unfilled, and the clauses have not been reviewed by a lawyer.
- Suggested model ids will drift as providers ship new models — use "Custom model…".
- Sarvam's `/v2/chat/completions` (glm5.3, gemma4, deepseekv4-flash) is not wired up; it
  needs per-key beta access.
