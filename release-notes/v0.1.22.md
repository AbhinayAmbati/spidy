# Spidey v0.1.22

Everything here came out of a single diagnostics report from a real run, which is why the
first item is about the diagnostics themselves.

## The task totals were never being saved

The report showed `model 0 ms / tokens 0 in / 0 out` while the per-step numbers underneath it
were correct. The totals existed on the model but had no column in the database, so the
mapper dropped them and every read came back as zero. A measurement that silently reports
zero is worse than no measurement, because it looks like an answer. Fixed, with a migration,
and there is now a test that fails if the two ever drift apart again.

What the real numbers showed, once summed from the per-step data: **the model was about a
third of the time, and waiting for the screen to settle was more than a third.** That
reframes where the work should go — the last two releases were aimed at model calls.

## Three faults that broke the run

**Opening an app failed if you named it rather than its package.** The tool's own description
promised it accepted an app name, and the code underneath could already resolve one — but the
check in front of it demanded a package and never let the call through. It accepts either now.

**Typing into a field failed on the first attempt and worked on the second**, repeatedly.
Setting text is refused by a field that does not hold focus, which several apps' search boxes
do. It now focuses the field first, clicking it if that is what the platform needs.

**Tapping autocomplete suggestions instead of submitting the search.** Those only refill the
search box, so the screen never changed and the agent looped until it stopped itself. The
prompt now says to submit — the magnifier, the Search action, or the keyboard's search key.

## It no longer pays to wait for screens it just read

Reading the screen cannot change the screen, so waiting for it to settle and then re-reading
it was pure cost — 300 ms a time. Those steps now return what they already read.
