# Spidey v0.1.17

## Fixed: touch-to-stop fired on window changes, not touches

**This is the real cause of the problem from v0.1.15 and v0.1.16.** I had hardcoded the
touch event constant as `0x00000020`. That value is `TYPE_WINDOW_STATE_CHANGED`. The constant
I wanted, `TYPE_TOUCH_INTERACTION_START`, is `0x00100000`.

So touch-to-stop was firing on **window changes** — and opening an app is a window change.
That matched a report of the agent stopping by itself while opening an app. You were right
that the agent's own movement was triggering it; I had the wrong event.

Production code now uses the **platform's own constants** rather than a mirrored number, so
this cannot drift again, and a test pins the mirrored value and asserts that window-change
events are never read as a touch. My earlier two attempts — the arming delay and the event
timing — were real improvements but were treating symptoms of this.

## Faster: the same screen, seen and acted on more cheaply

I audited the whole see-and-act path. A ten-step task was spending **6 to 40 seconds doing
nothing but waiting**, before the model was even called.

**The settle wait was polling the view tree.** After every action it walked up to 80 nodes,
twice, every 120 ms, for as long as four seconds — thousands of node visits on the main thread
per step. It now watches the platform's window-change events, which the service already
receives, so waiting costs one cheap read per tick and touches the tree not at all.

**Bounds were computed twice for every node in the tree.** The filter that runs on *every*
node read its screen bounds, and then each kept element read them again. Bounds are now read
once, and only for elements actually kept.

**Two tools were doing a full screen read for no reason.** `read_screen` took a whole snapshot
whose result was immediately thrown away and replaced by the runtime's own; `find_text` built
a full snapshot to answer a yes-or-no question. `swipe` built one just to learn the screen
size. All three are now cheap — a platform text search, and the display metrics.

**Net effect: exactly one full screen read per step**, where there were several.

**The listing now reads like the screen.** Elements are ordered top to bottom and left to
right instead of in accessibility-tree order, which has no relation to what you see. The
header also states whether the screen scrolls. Both exist so the agent stops scrolling blind
and re-reading — each blind attempt costs a whole step.

**New tests:** `SettleGateTest` and `VisualOrderTest`, plus a regression test for the
window-change bug.
