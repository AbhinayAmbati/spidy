# Spidey v0.1.18

Phases 0 and 1 of the performance work: measure first, then stop doing work that isn't needed.

## Measure first

Every number I have quoted you so far was computed from constants in the code, not measured on
your phone — and that gap is exactly how three regressions in a row got through. So the app now
measures itself.

**Every step is timed**: waiting on the model, settling, reading the screen, and performing the
action. Token usage is captured from all three providers (OpenAI, Anthropic, Gemini) so you can
see what a task actually costs.

**History → a task → Performance** shows the split: *waiting on the model* versus *on the
device*, plus tokens. Those two halves need completely different fixes, so it is worth knowing
which dominates your runs.

**Copy diagnostics** puts a full plain-text report on the clipboard — version, device, provider,
the timing split, and every step with its timings and failure reason. Paste it into a message
and a problem can be diagnosed from the report rather than a screenshot. It carries no screen
content beyond the failure reasons the app already shows.

## Stop doing work that isn't needed

**An action that changed nothing no longer re-reads the screen.** The settle wait now reports
whether any window-change event arrived; when none did, the screen is byte-for-byte what the
model already has, so both the tree traversal and the listing are skipped. This applies to every
no-op action, and it is the single biggest per-step saving.

**Settle shortened from 500 ms to 300 ms.** Settling is driven by the platform's own change
events rather than by polling, so a shorter quiet window is enough.

**`notificationTimeout` lowered from 300 ms to 100 ms**, so the change events that settle
detection depends on arrive sooner. This was putting a floor under how quickly a step could
finish.

Together these cut roughly 0.3–0.5 s from a settled step and considerably more from steps that
do nothing — and, for the first time, you will be able to see whether that is what happened.

**New tests:** `TaskDiagnosticsTest`, plus change-detection in `SettleGateTest`.

## What's next

Phase 2 is the one that actually gets a multi-step task under five seconds: **one model call
returns a short plan, executed locally, re-planning only on failure.** With one call per action,
a five-action task costs six seconds of model time before the phone does anything — no amount of
tuning fixes that. Phase 3 (recorded routines, replayed with no model at all) follows.
