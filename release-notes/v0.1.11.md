# Spidey v0.1.11

## What changed

**Element targeting is now stable.** Taps were aimed at a positional `[ref]`, which was an
index into a single screen snapshot — so the moment the screen changed, it pointed at
something else. That is why steps like *"Tapping element #17"* failed or landed on the wrong
thing. Each element now gets a short **key** derived from what it is (its id, widget type,
text and a bucketed position), so it still identifies the same element after a re-read and
simply disappears when it leaves the screen — a truthful failure instead of a wrong tap.
Keys are bucketed to 16 px, so layout jitter and scroll animations do not invalidate them,
while two identical rows in a list still get distinct keys.

**Scrolling works in both directions.** `scroll` used the first scrollable it found, which was
often a small nested region — hence *"Scrolling backward"* failing. It now uses the largest
scrollable region on screen, and falls back to a real drag gesture when an app ignores the
scroll action.

**The system prompt now spells out the workflow and every tool.** It previously listed rules;
it now describes the loop step by step — *read → decide → act → verify* — and explains when to
use each tool, including the three the agent gets wrong most: `press_back` (only to leave a
screen you just opened, never to look around), `press_home` (for switching apps), and `scroll`
(to reveal what is not yet listed). It also states plainly that a `[key]` from an older
observation must never be reused.

**Search is one step, and the prompt says how.** It gives the exact URL forms for web search,
YouTube and Maps, so searching does not mean driving a browser's interface by hand.

**A usage guide.** [docs/USAGE.md](docs/USAGE.md) covers setup, how the agent works, how to
phrase tasks, what each tool does and when it is used, worked examples, and a troubleshooting
table mapping the message you see to what to do.

**New tests** for element keys (`ElementKeyTest`) and the target schema.
